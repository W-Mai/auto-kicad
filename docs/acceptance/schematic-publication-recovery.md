# Durable schematic file publication and recovery

`ProjectWriter::prepare_schematic_publication` binds 1..32 explicit writes to exact existing-file digests or proven absence, complete candidate digests and deterministic sibling staging paths. Candidate files are bounded to 32 MiB each and 128 MiB total. A durable execution record and pending marker precede staging. Staged bytes and parent directories are synchronized before per-file publication. Existing destinations use checked renames; new destinations use exclusive hard links and staging removal, so a collision cannot overwrite another file. The publication guard borrows the writer lock and consumes its continuation on any uncertain IO result.

Execution schema 3 retains complete immutable `publication` intent. Recovery accepts a destination only at its exact before state or candidate state, including after a process exits without recording post-attempt fingerprints. Arbitrary later bytes reject even if an uncertain completion observed them. Staging paths must match the attempt identity, file ordinal and confined destination parent. A stage must be absent or exactly match the complete candidate digest; partial or different bytes require inspection and cannot be deleted by inferred ownership.

Recovery schema 4 exposes `staging_files` and `staging_files_restore_to: {"kind": "absent"}` alongside existing backups and new-source removals. These paths and their observed states participate in the recovery hash and fresh approval. Preparation, preview and commit recheck sources, backups and staging. Each file is checked again immediately before replacement/removal, parent directories are synchronized, and the complete restored set is verified before releasing the owning pending marker. An interrupted recovery can be planned afresh from still-exact before/candidate states; used approvals cannot resume.

This is a backend file IO contract. [Native committed results](schematic-native-publication.md) require an actual-source verification proof bound to the matched candidate. [Bounded schematic MCP](schematic-general-mcp.md) adds server-owned sessions and exact approval for supported existing-file editing. Publishing an unreferenced new schematic does not implement hierarchy creation. Concurrent external writers remain unsupported. Power-loss durability and every possible interruption during staging are separate from process-exit boundary checks; mismatched partial staging fails closed.

Architectural contracts cover every complete file boundary, missing terminal/post-attempt evidence, link/rename/directory-sync acknowledgement ambiguity, partial staging, journal drift, later user content, editor locks, source collisions, fresh recovery after partial restoration, and cross-state-directory write blocking. Native acceptance uses an owned multichannel copy with two property-edited existing files and an unreferenced new schematic. The acceptance executable exits a separate writer process with code 79 after staging and after each of three file publications, bypassing Rust destructors. Actual stdio MCP performs recovery; native audits independently compare the partial value edits and complete restored netlist/ERC/connectivity.
